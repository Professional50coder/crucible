# ERC-8004 and the Model Passport

Crucible does not currently mention ERC-8004 anywhere. This document works out whether it
should, and what it would honestly buy us.

Written **2026-08-16**. Every external claim below is either a direct quote from a primary
source or a read executed against a live 0G RPC endpoint on that date. Anything not verified
that way is marked **unverified**.

---

## 1. What ERC-8004 is

**[ERC-8004: Trustless Agents](https://eips.ethereum.org/EIPS/eip-8004)** — Standards Track ERC,
status **Draft**, created **2025-08-13**. It defines three registries that together give an AI
agent a public on-chain identity, a place for others to leave feedback, and a place for third
parties to record checkable verdicts about it.

| Registry | What it holds |
|---|---|
| **Identity Registry** | An ERC-721 token per agent, plus a URI and arbitrary key/value metadata |
| **Reputation Registry** | Signed feedback from clients — a score, tags, an off-chain URI and its hash |
| **Validation Registry** | A third party's checkable verdict on an agent — a request, then a response |

The EIP states its deployment expectation directly:

> we expect the registries to be deployed with singletons per chain

It gives **no addresses and no chain IDs**.

### The interfaces, as published

Identity Registry (extends ERC-721 with URIStorage):

```solidity
function register(string agentURI, MetadataEntry[] calldata metadata) external returns (uint256 agentId);
function register(string agentURI) external returns (uint256 agentId);
function register() external returns (uint256 agentId);
function setAgentURI(uint256 agentId, string calldata newURI) external;
function setMetadata(uint256 agentId, string memory metadataKey, bytes memory metadataValue) external;
function getMetadata(uint256 agentId, string memory metadataKey) external view returns (bytes memory);
function setAgentWallet(uint256 agentId, address newWallet, uint256 deadline, bytes calldata signature) external;
function getAgentWallet(uint256 agentId) external view returns (address);
function unsetAgentWallet(uint256 agentId) external;

event Registered(uint256 indexed agentId, string agentURI, address indexed owner);
event MetadataSet(uint256 indexed agentId, string indexed indexedMetadataKey, string metadataKey, bytes metadataValue);
event URIUpdated(uint256 indexed agentId, string newURI, address indexed updatedBy);
```

Validation Registry — the one a Model Passport structurally resembles:

```solidity
function validationRequest(address validatorAddress, uint256 agentId, string requestURI, bytes32 requestHash) external;
function validationResponse(bytes32 requestHash, uint8 response, string responseURI, bytes32 responseHash, string tag) external;
function getValidationStatus(bytes32 requestHash) external view returns (address validatorAddress, uint256 agentId, uint8 response, bytes32 responseHash, string tag, uint256 lastUpdate);
function getSummary(uint256 agentId, address[] calldata validatorAddresses, string tag) external view returns (uint64 count, uint8 averageResponse);
function getAgentValidations(uint256 agentId) external view returns (bytes32[] memory requestHashes);
function getIdentityRegistry() external view returns (address);

event ValidationResponse(address indexed validatorAddress, uint256 indexed agentId, bytes32 indexed requestHash, uint8 response, string responseURI, bytes32 responseHash, string tag);
```

An attestation therefore carries: a validator address, an `agentId`, a **`uint8` response**
(the EIP: *"response is a value between 0 and 100"*), a `responseURI`, a `responseHash`, a
free-text `tag`, and a `lastUpdate` timestamp. That is the whole payload. Note what it is:
a **score plus a pointer**. It is not a structured record.

The Reputation Registry is omitted here because, as §3 explains, nothing in a passport maps to it.

### What 0G says

From 0G's own [Agentic ID page](https://docs.0g.ai/concepts/agentic-id), verbatim:

> Agentic IDs are compatible with **ERC-8004**, the Trustless Agent standard that 0G officially supports.

> An Agentic ID can carry a corresponding ERC-8004 registration, making the agent discoverable and interoperable across the ERC-8004 ecosystem.

The same page describes ERC-7857 as extending ERC-721 with *"Encrypted metadata storage for
protecting AI intelligence"*, and introduces ERC-8004 only in terms of discoverability and
interoperability. The division that suggests — 7857 for encrypted metadata, 8004 for public
discoverability — is our reading of those two quotes, not a sentence 0G writes.

**That page lists no contract addresses.** 0G says it supports the standard; it does not, on
that page, tell you where the registries are.

## 2. Deployment reality — checked against the live network

This is the fact that decides everything else, so we did not take it from a page.

The registries curated by the 8004 team ([`erc-8004/erc-8004-contracts`](https://github.com/erc-8004/erc-8004-contracts))
list 0G among their deployments. We read those addresses off the chain itself.

**Executed 2026-08-16 against `https://evmrpc-testnet.0g.ai` and `https://evmrpc.0g.ai`:**

| Chain | Contract | Address | Live result |
|---|---|---|---|
| Galileo **16602** (`eth_chainId` → `0x40da`) | IdentityRegistry | `0x8004A818BFB912233c491871b3d84c89A494BD9e` | has code · `name()` = `AgentIdentity` · `symbol()` = `AGENT` · `supportsInterface(0x80ac58cd)` = `true` |
| Galileo **16602** | ReputationRegistry | `0x8004B663056A597Dffe9eCcC1965A193B7388713` | has code · `getIdentityRegistry()` = `0x8004A818…BD9e` ✅ points at the identity registry above |
| Mainnet **16661** | IdentityRegistry | `0x8004A169FB4a3325136EB29fA0ceB6D2e539a432` | has code · `name()` = `AgentIdentity` · `symbol()` = `AGENT` · ERC-721 ✅ |
| Mainnet **16661** | ReputationRegistry | `0x8004BAa17C55a88189AE136b182e5fdA19dE9b63` | has code · `getIdentityRegistry()` = `0x8004A169…a432` ✅ |

They are not empty. `tokenURI(1)` resolves on both chains — `https://metadata.test.evoevo.ai/agents/126`
on Galileo, `https://metadata.evoevo.ai/agents/3151` on mainnet — so agents are already registered
by someone other than us.

They are ERC-8004-shaped, not merely ERC-721. On the Galileo identity registry both of these
returned data rather than reverting:

- `getAgentWallet(1)` → `0xc6fb5cc21608a0e9361768ba6464f5a8ff0d908c`
- `getMetadata(1, "agentName")` → empty `bytes` (the call succeeded; the key is simply unset — this is not evidence the key is unsupported)

**So: yes. ERC-8004 Identity and Reputation registries are deployed and live on both 0G Galileo
and 0G mainnet.** Option (b) below is real, not hypothetical.

### The catch, and it is the important one

**There is no Validation Registry.** We found no Validation Registry address for 0G, and the
8004 team's own repository lists none for *any* chain, with this reason:

> The Validation Registry portion of the ERC-8004 spec is still under active update and discussion with the TEE community.

> This section will be revised and expanded in a follow-up spec update later this year.

The registry a Model Passport actually fits is the one that does not exist yet. Everything in §4
follows from that.

### What we did **not** verify

- We did not check whether these contracts are **source-verified** on chainscan.
- The Galileo registries are **EIP-1967 proxies** — the deployed bytecode is the minimal
  delegating stub, and the implementation slot holds `0x7274e874ca62410a93bd8bf61c69d8045e399c02`.
  We did **not** determine who controls the upgrade admin, so the code answering our calls today
  can be replaced by someone we have not identified. **Material.** We did not check the proxy
  pattern on the mainnet pair — **unverified**, though the identical bytecode size and identical
  responses make it likely.
- The deployed contract does **not** match every signature in the current draft: `getAgentURI(uint256)`
  and `getIdentityRegistry()` both **reverted** on the identity registry, and `totalSupply()`
  reverted (it is not ERC-721 Enumerable). It tracks *some* version of a moving Draft. Any ABI
  we write must be built against the deployed bytecode, not against the EIP text.
- We sent **no transactions**. Every result above is `eth_call` / `eth_getCode` / `eth_getStorageAt`.
  Whether `register()` is permissionless in the deployed implementation is **unverified** — the
  published interface shows no access control, but we did not test it.
- Whether 0G itself regards these as *the* canonical registries for the chain is **unverified**.
  The Agentic ID page claims support for the standard but names no addresses; we did not search
  the rest of 0G's documentation for one.

## 3. The mapping

A Model Passport ([`packages/core/src/passport.ts`](../packages/core/src/passport.ts)) is a
canonical JSON manifest, keccak256-hashed, stored on 0G Storage, its hash anchored in
`Passport.sol` on Galileo at `0x27087B5bD124f2a570eb22B6B5bbe05F5d83C1c7`.

Structurally it is a **third party's checkable claim about a model** — which is exactly what the
Validation Registry is for. It is not feedback and it is not an identity.

### What maps to the Validation Registry

| Passport field | ERC-8004 field | Fit |
|---|---|---|
| `manifestRootHash` (the keccak256 anchor) | `responseHash` (`bytes32`) | Clean. Same shape, same purpose |
| 0G Storage URI of the manifest | `responseURI` (`string`) | Clean |
| The Crucible attester address | `validatorAddress` | Clean |
| "this is a lineage record" | `tag` (`string`) | Workable — free text, e.g. `lineage` |
| `mintedAt` | `lastUpdate` | Set by the registry, not by us |

### What maps to the Identity Registry

| Passport field | ERC-8004 field | Fit |
|---|---|---|
| Manifest URI | `agentURI` via `register(string)` | Workable |
| `base.modelHash`, `dataset.rootHash`, `training` config hash, `adapter.rootHash`, `manifestRootHash`, `task.id`, `task.provider` | `setMetadata(agentId, key, bytes)` | Workable but **lossy in meaning** — it is an untyped key/value bag. Nothing enforces the keys, so nothing reading the registry knows what they mean without our documentation |

### What does **not** map — be specific

- **`agentId`.** ERC-8004 hangs everything off a `uint256 agentId` in the Identity Registry.
  A passport describes a **model artifact** — a LoRA adapter — not an agent. To use the
  Validation Registry at all we would first have to register the model *as an agent*, which is
  a category claim we may not want to make.
- **The `uint8` 0–100 response.** A passport is not a score. There is no honest value to put
  there. Writing `100` would assert a quality judgement the passport does not make; writing
  anything else would be equally invented. This is the deepest mismatch and it is not cosmetic.
- **The fee block** (`fee.trainingNeuron`, `fee.storageReserveNeuron`, `fee.totalNeuron`).
  No ERC-8004 field carries cost. It survives only inside the manifest behind `responseURI`.
- **The TEE block** (`tee.signerAddress`, `tee.acknowledged`, `tee.attestationVerified`).
  A single `uint8` plus a `tag` cannot express "signer X, acknowledged, attestation **not**
  verified". Collapsing it loses precisely the nuance the passport exists to preserve.
- **`dataset.exampleCount` / `tokenCount`, `adapter.sizeBytes`, `base.tokenizer`, `network`,
  `chainId`, `createdAt`.** No fields. Manifest-only.
- **The authorization surface.** `authorizeUsage`, the executor set, and clearing on transfer
  are ERC-7857 concerns. ERC-8004 has no concept of authorization at all. Zero overlap.
- **The entire Reputation Registry.** A passport carries no opinion, no rating, and no client
  feedback. Nothing in it maps here. We should say so rather than reach for a fit.

The honest summary: **the half of ERC-8004 that fits a Model Passport is not deployed on 0G,
and the half that is deployed fits it worst.**

## 4. Three options, ranked by cost

### (a) Documentation-only alignment — zero contract change

**Requires:** this file, kept current; the mapping table above published; optionally a
`--erc8004` flag on the passport CLI that prints the manifest in ERC-8004-shaped JSON so the
correspondence is mechanical rather than prose.

**Costs:** no gas, no contract change, no new trust assumption. Author time only.

**Buys:** a precise answer to "how does this relate to the standard 0G officially supports",
in the standard's own vocabulary, without claiming anything we have not done. It also documents
the *mismatch* — the `uint8` score problem and the missing Validation Registry — which is
information the ecosystem does not currently have written down anywhere we found.

**What could go wrong:** it is paper. Anyone can point out we did not actually integrate.
And ERC-8004 is **Draft** — the Validation Registry section is explicitly still moving, so this
mapping will need re-checking, not just re-reading.

### (b) Register in the live 0G Identity Registry — one transaction

Now known to be possible: the registries in §2 are live on Galileo **16602** and mainnet **16661**.

**Requires:** an ABI built against the **deployed bytecode** (not the EIP text — see the reverting
signatures in §2); one `register(string agentURI)` call with the manifest URI; then one
`setMetadata` call per lineage field. For scale: our `Passport.sol` mint cost **327,702 gas**
([`CLAIMS_AUDIT.md`](CLAIMS_AUDIT.md)), and these calls are comparable in shape. That is an
order-of-magnitude reference, not an estimate — we have not simulated these calls.

**Buys:** the passport becomes discoverable to any ERC-8004 indexer on 0G. This is the concrete
form of 0G's own sentence — *"An Agentic ID can carry a corresponding ERC-8004 registration"* —
and it is a real cross-standard link rather than a described one.

**What could go wrong:**
1. We would be writing into an **upgradeable proxy whose admin we have not identified** (§2).
   Our attestation's meaning depends on code someone else can replace.
2. It registers a **model as an agent**. That is a claim about what the artifact *is*, and it is
   not obviously true.
3. It uses the Identity Registry as an untyped metadata bag — the weaker half of the fit —
   while the Validation Registry, which actually matches, stays unused.
4. Permissionless registration is **unverified**; the call may revert for reasons we have not tested.
5. Someone reading the registry could mistake "registered" for "verified". It is not.

### (c) Deploy the registries ourselves

**Requires:** implementing `IValidationRegistry` against a Draft whose validation section the
authors describe as *"still under active update and discussion"*, deploying it, pointing its
`getIdentityRegistry()` at the existing 0G identity registry, and maintaining it. For scale,
deploying `Passport.sol` cost **2,238,586 gas** ([`CLAIMS_AUDIT.md`](CLAIMS_AUDIT.md)); a
Validation Registry is a different contract and we have not sized it.

**Buys:** the only option that gives the structurally correct fit — a real attestation in the
registry the passport actually resembles.

**What could go wrong:** the EIP says *"we expect the registries to be deployed with singletons
per chain"*. Ours would not be the singleton. If the 8004 team later deploys the canonical
Validation Registry on 0G, every attestation we wrote sits on an orphaned contract and the work
is worse than wasted — it is misleading. We would also be implementing a spec section its own
authors say is about to change, and taking on audit surface for a contract that is not our
product.

## 5. What this would **not** let us claim

Under any of the three options:

- **It does not make the training honest.** An attestation records that the lineage is what we
  say it is. Whether the provider actually ran the epochs still requires ZK proofs over the
  training computation — PEFT-restricted update circuits enforcing optimizer semantics, per
  [arXiv:2510.16830](https://arxiv.org/abs/2510.16830). Crucible proves **lineage, not honest
  training**, and an ERC-8004 record does not move that line by one inch.
- **It does not make `Passport.sol` ERC-7857 compliant.** Different standard, different gap.
  `Passport.sol` implements the identity and `authorizeUsage` surface but not `transfer()` with
  oracle re-encryption or `clone()`. ERC-8004 has nothing to say about that, so registering
  changes nothing about the "-style" qualifier, which stays.
- **It does not make Crucible "ERC-8004 compliant."** That phrase means implementing a registry
  interface. Under (a) and (b) we would be a *user* of the registries, not an implementation of
  them. Only (c) would make the word "compliant" applicable, and only to the contract we deployed.
- **Registration is not verification.** Anyone able to send a transaction can register. A record
  in the Identity Registry attests to nothing but the fact that someone paid gas.
- **Self-attestation is not third-party validation.** The Validation Registry's value comes from
  the validator being independent of the agent. Crucible attesting to passports Crucible minted
  is a loop. It would be legible, but it would not be evidence.
- **It buys no reputation.** Nothing in a passport maps to the Reputation Registry, so no
  amount of integration produces a reputation signal.

---

## 6. Recommendation

**Do (a) now. Treat (b) as an optional, clearly-labelled experiment. Do not do (c).**

Reasoning:

1. **The fit is with the Validation Registry, and it is not deployed on 0G.** We confirmed this
   against the live chain and against the 8004 team's own repository. Building toward the
   registries that *are* live means building toward the half that matches worst.
2. **The `uint8` 0–100 response has no honest value for a lineage record.** Until that is
   resolved — and the authors say the validation section is still being discussed — any
   attestation we emit would contain at least one invented number. That fails this repository's
   standing rule on its own.
3. **(c) risks being actively misleading.** A non-canonical singleton that gets superseded is
   worse than an absence.
4. **(a) costs nothing and is the part with real value.** The mapping — including the honest
   statement of what does not map — is information that did not exist in writing before this
   document. That is worth more right now than a transaction into a proxy we do not control.

If (b) is later attempted, it must be recorded in `FIELD_NOTES.md` with its transaction hash,
like every other on-chain claim in this repository, and it must be described as *"registered"*,
never as *"verified"*.
